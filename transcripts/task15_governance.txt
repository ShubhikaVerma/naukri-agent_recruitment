HIGH. The assistant reads individual job-application records, including expected salary (financial data), and produces an escalation recommendation that can influence how a candidate's application is handled, so it sits next to hiring decisions even though it is read-only and never decides anything itself. Answering policy questions alone would be Medium (customer support), but errors or leaks here affect real people's employment and pay, so the stricter controls apply: least autonomy, phone-number masking, groundedness refusal, an independent review team, a per-request token budget, and structured audit logging. This project uses fabricated data only.

How the guard works:
Each tool instance is bound to one agent role, and ALLOWED_TOOL_ROLES says which roles may use which tool: only the Lookup Agent may use check_job_application_status, and only the Retrieval Agent may use rag_lookup. The guard has two layers. At wiring time make_agent() refuses to attach a tool to any agent whose role does not match the tool's binding or is not on its allow-list, so wiring the lookup tool to the Response Composer raises LeastAutonomyViolation before the crew exists. At call time the tool checks its own bound role again before running, so even code that builds an Agent directly and skips make_agent() is stopped when it tries to call the tool. The Composer has no tools at all: it can only combine what the other agents report.
